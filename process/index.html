Process

From possibility to a product you own.

The process is not a ceremony or an endless slide deck. It is a disciplined sequence that removes ambiguity, tests decisions against real conditions, and ends with software that works in everyday use.

System
Seven stages, each with an explicit decision and output.
Entry routes
Tailored whether you start from a defined project or an early idea.
Ownership
Agreed before the build starts, not negotiated at handover.

What you keep when the work is done

  • You own the code and the repository.
  • You own the hosting, domain, and service accounts.
  • You receive written documentation for the system as built.
  • Deployment and maintenance responsibilities are explained in plain language.
  • No lock-in: the work can be maintained by anyone you choose.

Ownership is stated in the scope before work begins. Handover is a stage, not a negotiation.

Two routes into the work

Where we start depends on how far your thinking has already progressed.

Route A · High clarity

A defined project

You understand the problem, know who will use the product, and know which tasks must change. Work moves quickly from requirements confirmation into design and build.

Route B · Exploratory

The seven stages

  1. Stage 01UnderstandA written problem statement and the constraints that shape it.
  2. Stage 02DefineA scope with deliverables, exclusions, dependencies, and a definition of done.
  3. Stage 03DesignApproved screens, user flows, and content structure before code.
  4. Stage 04BuildA working increment on a staging link, built against the agreed scope.
  5. Stage 05ReviewA signed-off release after real-device, browser, and accessibility testing.
  6. Stage 06HandoverCode, accounts, documentation, and a walkthrough in your name.
  7. Stage 07ContinueAn agreed maintenance arrangement and evidence for the next release.

Stages are not a fixed calendar. Small releases move faster; operational systems spend longer in Understand and Review. What does not change is that each stage ends with a decision you can point to.

What we insist on

A defined first release

Not every possible feature belongs in version one. The first build is protected around the core outcome; later features are decided once real users have used it.

Written agreements and scope

Scope, deliverables, timing, cost, and ownership are established in writing before work begins. No hidden retainers, surprise fees, or lock-in clauses.

Real user conditions

Requirements reflect the actual phones, network speeds, cash handling, and physical conditions the product will live in — not a fast connection in a quiet room.
