What changes hands

The handover is a checklist, not a promise.

A product is not handed over because the work is finished. It is handed over when the client can operate, change, and defend it.

A checklist is not a promise. It is a list of things that must be true before the work changes hands.

  • 01
    Repository with historyThe full source, not a flat export.
  • 02
    Hosting and domain accountsIn the client’s control, with access confirmed.
  • 03
    Setup and deployment documentationWritten for the person who comes next.
  • 04
    Deployment walkthroughA live pass through publishing and rolling back.
  • 05
    Content and admin notesWhat can change without an engineer.
  • 06
    Maintenance responsibilityA named owner, or a clean exit to another team.
  • 07
    Ownership confirmationA written record of what has transferred.

Seven stages

One system, from first conversation to a named owner.

Every stage has an input, a defined piece of work, an output, and the decision that lets the work move on.

  1. 01

    Understand

    Input
    The situation, the current tools, and the constraint that matters most.
    Work
    Listen, inspect the current flow, and ask for the evidence behind the problem.
    Output
    A written situation summary and the scope boundary.
    Exit decision
    The problem is clear enough to define.
  2. 02

    Define

    Input
    Priorities, the people affected, and the first release the business can support.
    Work
    Define the first release, roles, the observable change, and what is deliberately excluded.
    Output
    A scope and release definition with exclusions.
    Exit decision
    The scope is agreed in writing.
  3. 03

    Design

    Input
    Real content, the brand, and examples from the actual workflow.
    Work
    Structure the flow, design the interface, cover the states, and review accessibility.
    Output
    A reviewed interface design for the release.
    Exit decision
    Flows, states, and content are agreed.
  4. 04

    Build

    Input
    Content, accounts, and the decisions recorded in the design.
    Work
    Implement, version the work, and test the parts that carry the most risk.
    Output
    A staging build that matches the agreed scope.
    Exit decision
    The build is ready for review.
  5. 05

    Review

    Input
    The staging build and the devices, browsers, and roles that matter.
    Work
    Check keyboard use, responsive widths, content, links, contrast, and form states.
    Output
    A review record and the fixes that came from it.
    Exit decision
    The release criteria are met.
  6. 06

    Handover

    Input
    Accounts, domain access, and the people who will operate the product.
    Work
    Transfer the work, document it, and walk through deployment and ownership.
    Output
    Repository, accounts, documentation, walkthrough, and ownership confirmation.
    Exit decision
    The client can operate the product.
  7. 07

    Continue

    Input
    Live feedback and a prioritised change list.
    Work
    Maintain, fix, or evolve the product, or prepare a clean exit to another team.
    Output
    A maintenance plan or a documented exit.
    Exit decision
    Responsibility is named.

Ownership

What you keep.

The product should be operable by someone else. Ownership is the point of the work, not a retention strategy.

  • ✓The source code and its history.
  • ✓The hosting, domain, and service accounts.
  • ✓The documentation needed to run and deploy the product.
  • ✓A walkthrough of the deployment and the points of risk.
  • ✓A maintenance decision that belongs to the client, not a condition of the work.

Ownership is confirmed in writing at handover. The engagement itself is governed by a separate agreement, not by this website.
